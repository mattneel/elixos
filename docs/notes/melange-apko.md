# melange and apko on this machine

What M16 (the Alpine image build, ADR-041) cost to learn. The build tools
themselves are pinned in `scripts/install-build-tools.sh` (melange v0.62.0,
apko v1.4.10, both by sha256).

## melange

- Building the kernel's `tools/` (objtool) needs a system `asm/types.h`: on
  Alpine that is the `linux-headers` package, on glibc distros it is there
  already (linux-libc-dev). Without it objtool fails with "asm/types.h: No such
  file or directory".
- The x86_64 kernel build also needs `gawk`. BusyBox awk rejects the literal
  `{` in mainline `scripts/orc_hash.sh`; its pipeline can still exit zero and
  emit the hash of empty input. Adding `gawk` to the melange build environment
  fixes the ORC metadata without patching Linux. A fresh packaged build must
  have no `awk: bad regex` warning as well as passing the config guard.
- `--source-dir` does **not** bind your tree read-only: melange *copies* it
  into its workspace, which it then binds at `/home/build`. Pointing it at the
  repo root once copied 55G (the kernel tree, `os/_build`, `os/tmp`). Stage a
  small directory instead - only what the package's pipeline reads. Dotfiles
  (`.zig-version`, `.tool-versions`) must be named explicitly when staging;
  the package pipelines read them for their version assertions.
- The copy is writable, so a pipeline can build in place (`cd /home/build`);
  no copying into `/tmp` is needed.
- `melange keygen` writes `melange.rsa`/`melange.rsa.pub`. The private key is
  the dev signing key: `build/` is gitignored, so it stays out of git.
- `--out-dir` becomes an APK repository (an `APKINDEX` is generated by
  default); apko consumes it with `-r`/`--repository-append` and the public key
  with `-k`/`--keyring-append`.
- aarch64 packages on an x86_64 host run under binfmt emulation
  (`qemu-aarch64` registered, docker for the `docker` runner if wanted). This
  machine has both; `scripts/check-tools.sh` reports them.
- The first aarch64 image build on this x86_64 WSL host took 5,143 seconds;
  the next `make image` assembled both architectures from cached APKs in
  51 seconds. Kernel-fragment preflight is cheap; emulated kernel and OTP
  compilation is not. Delete only the APK whose sources changed to rebuild
  it, or use `FORCE=1` when every package really needs rebuilding.
- A cold on-box C toolchain smoke in a 1 GiB aarch64 TCG guest took 480
  seconds: the pinned Zig ran, the `cc` bridge built a static musl binary,
  that binary exited 23, and the VM cwd stayed `/`. Keep this separate from
  the boot/save/restore smoke, which does not run the native C compiler.
- The build environment needs its own packages (busybox, curl, tar, xz for the
  shim); the repositories in the YAML are the same pinned Alpine release apko
  uses.
- A melange APK is a plain tar stream as far as `tar` is concerned: `tar -xzf
  pkg.apk` works, without apk-tools on the host (`apk` itself is not installed
  here). The checksum xattr is just a warning (`--warning=no-unknown-keyword`),
  and naming the directories wanted (`tar -xzf pkg.apk -C dir toolchain`) skips
  the `.PKGINFO`, signature and SBOM metadata.
- Kernel fragments are named after melange's `build.arch` values - `x86_64`
  and `aarch64` - because the kernel package reads
  `kernel/config.${{build.arch}}`. An `arm64` file builds nothing and fails
  with "The merge file .../config.aarch64 does not exist".
- The common kernel fragment must stay arch-neutral: `CONFIG_I6300ESB_WDT` and
  `CONFIG_SERIAL_8250*` are x86 symbols, and the per-architecture guard fails
  the arm64 build on them (that is the guard doing its job).
- Kernel fragments can be pre-flighted on the host in seconds - `make
  ARCH=arm64 defconfig`, `merge_config.sh`, `make olddefconfig`, then
  `scripts/check-kernel-config.sh` - before paying for an emulated build.
  `unset LLVM` first: this machine's environment exports `LLVM`, and kbuild
  refuses ("Invalid value for LLVM").

## apko

- `apko lock <config>` exists but is hidden from `apko --help`. The lockfile
  is bound to the config's **checksum**: change the config and every build
  fails with "checksum ... does not match ... (maybe regenerate the lock
  file)". So locks are per package set and per architecture, and a config
  change means `apko lock` again.
- `apko build` emits an OCI-shaped tar (a `*.tar.gz` layer, `manifest.json`,
  `index.json`), takes `--lockfile`, `--build-date` (reproducibility),
  `--sbom-path` (SPDX, one entry per package with its version) and
  `--cache-dir` (our local mirror).
- `apko build-minirootfs` has **no** `--lockfile` and takes `--build-arch`
  instead of `--arch`; use `apko build` and take the layer.
- Keys can be committed: the config's keyring may name a repo-local path
  (`apko/keys/...`), and the lockfile embeds the key material too.
- Include `alpine-release=3.24.2-r0` in every melange build environment and
  the service image, as the factory already does. The package supplies real
  `/etc/os-release`; omitting it makes apko warn about missing release metadata.
  Do not suppress the warning or invent a distro file outside the package
  database. Actual metadata probes passed in all six build environments on
  both architectures, and both service-image builds completed without that
  warning.
- The layer's device nodes cannot be extracted without root. They do not need
  to be: the tar carries major/minor, and `gen_init_cpio` can declare them.

## Packing the initramfs

- `paths` is a top-level key in apko's config, **not** under `contents`; it is
  how a directory that no package ships exists at all. A missing `/priv` sent
  the first apko boot straight to rescue (`Elixos.info` said `mode: :rescue`):
  the shim cannot mount the persistent disk onto a path that is not there.
- Do not mix pipelines inside one root filesystem. Overlaying the old
  hand-built `/lib/ld-musl-x86_64.so.1` on Alpine's makes BusyBox segfault
  (exit 139) while the old factory still runs. During the transition, keep
  Alpine's loader and let the old ERTS use it.
- `gen_init_cpio` list syntax, per entry kind:
  - `dir <name> <mode> <uid> <gid>`
  - `file <name> <location> <mode> <uid> <gid>` - location before the mode,
    unlike the others (getting this wrong is "Unrecognized file format")
  - `slink <name> <target> <mode> <uid> <gid>`
  - `nod <name> <mode> <uid> <gid> <c|b> <major> <minor>`
- `-t 0` stamps every entry at the epoch; `gzip -9n` (no name, no timestamp)
  makes the archive reproducible.
- `scripts/mkinitramfs.sh` reads the layer tar with python3 and emits that
  list: ownership, modes and device nodes come from the tar, so nothing in the
  packing path needs root.

## The factory release and OTP

- `mix release` with `include_erts: false` takes the ERTS *and the OTP
  applications* from the system: the release carries only this project and its
  Hex dependencies. Elixos installs OTP as its own package (`elixos-otp`) and
  the release points at it - `/factory/erts` and `/factory/erts-<vsn>` as
  symlinks to the install, plus a symlink for every app in the OTP install's
  `lib/` that the release does not carry itself. Without those links the BEAM
  starts and dies before the prompt (it writes a crash dump under
  `/priv/crash/`), because the boot script's `$ROOT/lib` is the release's.
- The same package makes `erl` a symlink to `erlexec` inside the installed
  ERTS and copies the headers to `erts-<vsn>/include`, which is where
  `:code.root_dir()` sends a NIF build.

## Caching native builds (M19)

- The pinned Zig compiler used to be downloaded inside melange's *workspace*,
  which melange deletes after every build (`os.RemoveAll(WorkspaceDir)`), so
  every `make image` paid for two toolchain downloads (one per architecture)
  plus a full rebuild.
- An APK's existence is not evidence that it is current: the old rule
  ("`elixos-factory-*.apk` is there, skip") silently kept a factory built
  before the code changed, which is how an image can ship the wrong OS.
  `scripts/build-image.sh` now hashes each recipe's *staged* inputs - the
  `.tool-versions`/`.zig-version`, the melange YAML, the source tree that
  package reads, plus this script, the melange binary and the signing key -
  and stores `sha256(inputs) sha256(apk) filename` in
  `build/apk/<arch>/<arch>/.elixos-<pkg>.inputs`. A hit also re-checks the APK
  hash, so a stamp cannot outlive the bytes it describes, and `FORCE=1`
  rebuilds regardless. Commits that touch nothing a package reads (docs, a
  demo) rebuild nothing.
- `--cache-dir` is bind-mounted at `/var/cache/melange` and survives the
  workspace wipe: keep the compiler SDK under `.../zig/sdk/<tarball sha256>`
  (one download for both architectures; only `-Dtarget` differs) and Zig's own
  caches under `.../zig/global/<sha>` and `.../zig/local/<arch>`, so a
  one-line Zig change recompiles instead of rebooting the toolchain.
- The Zig compiler for a melange build runs on the *build host*, not in the
  package's target environment: an aarch64 package environment still needs an
  x86_64 compiler when the host is x86_64. The host architecture travels in
  `--env-file` (`ELIXOS_ZIG_HOST_ARCH`), and `-Dtarget=<arch>-linux-none` does
  the crossing (ADR-003: the shim has no libc).

## What the aarch64 build actually runs, and what could stop being emulated

On an x86_64 host the aarch64 packages are built inside an aarch64 Alpine
environment whose binaries run through `binfmt_misc` + `qemu-aarch64-static`
(`make check-tools` reports both). Emulation is not a property of "building
for aarch64" - it is what happens when the build has to *execute* target
binaries. Per package:

| package | how it is built today | could avoid emulation? |
|---|---|---|
| `elixos-shim` | `zig build -Dtarget=aarch64-linux-none` natively | already cross, no emulation |
| `elixos-toolchain` | prebuilt aarch64 compiler tarball; `cc` bridge via `zig build-exe -target aarch64-linux-musl` | already cross |
| `elixos-kernel` | full kernel `make` in the aarch64 environment | yes: `LLVM=1` (clang/lld) or `zig cc` as `CC` with `-target aarch64-linux-none`; medium risk, saves the kernel build time |
| `elixos-elixir` | `make` + an ERTS in the aarch64 environment | yes: Elixir is *pure BEAM*; bytecode built by any ERTS runs anywhere. Building it in the x86_64 environment (with the x86_64 `elixos-otp`) produces the same artifacts |
| `elixos-factory` | `mix deps.get` + `mix release` in the aarch64 environment | yes, for the same reason: `include_erts: false` (ADR-041) and every dependency is pure BEAM, so the release is bytecode plus `.boot` files. The symlinks it writes (`erts`, `erts-<vsn>`, `lib/<app>`) are absolute paths that resolve inside the target image, so they are identical either way |
| `elixos-otp` | `configure && make` in the aarch64 environment (the expensive one, ~10-15 min emulated) | only a real cross build: `--host=aarch64-linux --build=x86_64-linux` with `erl_xcomp_*` variables and a *bootstrap ERTS of the same version for the build host* (the x86_64 `elixos-otp` we already build). The C parts then compile with a cross compiler; the JIT's `configure` runtime checks are the fiddly part |

Alpine's own aarch64 packages are never built here - they are downloaded from
the pinned repository - so the table above is the whole cost.

Two consequences worth remembering:

* The cheapest change is elixir + factory: build them in an x86_64
  environment (pure bytecode), publish them with `--arch aarch64`, and gate it
  on `test/integration/m16_aarch64_test.exs` (a real boot, a saved module, a
  power cycle on an aarch64 guest). That removes both of the smaller emulated
  builds.
* Nothing above is needed for the *recurring* cost: the input-keyed cache
  (`## Caching native builds`) already rebuilds OTP only when its recipe or
  version changes, so the emulated OTP build is paid once per OTP bump, not
  once per `make image`.

## Test hygiene

- The QEMU harness reads prompts off the console, and `QEMU.iex/3`'s contract
  is a console sitting at a prompt the harness has already consumed. A test
  that types several expressions must thread the VM between the calls: M14's
  two-repo test used a `for` comprehension, dropped each iteration's VM, and
  typed into a console two prompts ahead of what the harness believed - the
  harness then matched the prompt still on screen and returned the echoed
  input alone, about one run in three. It looked like a harness timing bug for
  a while; ADR-042 records the rule. `iex/3` also anchors on the echo of the
  line it sent (whitespace flexible; a five-second window, because a
  multi-line expression's redraws can split the echo) and compares each
  matched prompt by its own number. Keep expressions short anyway.
- A killed QEMU run leaves its `@moduletag :tmp_dir` behind, and each holds a
  copy of the disk image: `os/tmp` reached 19G once. When the disk looks
  wrong, `rm -rf os/tmp/*` is safe - the tests recreate it.
- A daemon returned by `:ssh.daemon/2` is already a child of OTP's
  `:sshd_sup`. Returning that PID as an Elixos supervisor child does not
  reparent it: Elixos's shutdown signal is not from its parent, so Elixos
  waits five seconds and force-kills it. The aarch64 demo exposed the
  resulting `{:sshd, :acceptor_sup}` crash report. `Elixos.SSH` now owns a
  small GenServer that traps exits, monitors the daemon and calls
  `:ssh.stop_daemon/1` on termination. The regression checks normal daemon
  exit, EOF on an open connection and refusal of new connections.

## Service images (M18)

- Declaring `/dev/shm` in apko does not survive mounting devtmpfs on `/dev`.
  PID 1 must recreate that directory after devtmpfs, then mount its mode-1777
  tmpfs. Otherwise the base-mount failure sends an ordinary boot to rescue.
- A changed kernel fragment does not change an already cached native APK.
  Rebuild `elixos-kernel` for the affected target and run the fragment guard
  against that package's actual `.config`. The old x86_64 package lacked
  SquashFS even though the new fragment required it.
- Moving Alpine's library closure under `/system` does not relocate
  compiled-in data paths. `initdb` reached ICU's `und` locale and failed with
  `U_FILE_ACCESS_ERROR` until `/system/usr/share/icu` was exported at
  `/usr/share/icu`; PostgreSQL likewise needs timezone data at
  `/usr/share/zoneinfo`. Both exports are read-only bind mounts, normal mode
  only, released before the service image (ADR-052).
- Host image outputs are deliberately mode 0444. Replace a previously built
  `system.squashfs` with `install -m0444`, not `cp` onto its unwritable inode,
  so a second build succeeds without making the shipped image writable.


## Cross-building OTP (the one emulated step left)

After ADR-060, an aarch64 image build is: the native kernel cross (~5 min), the
native Elixir/factory reuse (seconds), Zig-crossed shim and toolchain (~5 min),
the assembly (~9 min) - and **OTP**, which is still built under
`qemu-aarch64-static` (~13 min). With the input-keyed cache that cost is paid
only when OTP's own recipe or `.tool-versions` change, not per build, which is
why it is the last item rather than the first.

Cross-compiling it is a bounded project, and the pieces are known:

* **A target sysroot.** ERTS links openssl (dynamic ssl), ncurses (termcap for
  the shell) and zlib, and needs musl's headers. All of them are aarch64
  Alpine packages: `apk fetch --arch aarch64 <deps>` then plain `tar -x` into a
  sysroot directory (no root, no second toolchain - `scripts/mkdisk.sh` already
  extracts an aarch64 APK the same way). Musl itself comes from Zig, so
  `zig cc --target=aarch64-linux-musl --sysroot=<dir>` is the whole compiler.
* **A bootstrap ERTS of the same version for the build host.** OTP's cross
  build compiles Erlang sources with an `erl` running on the build machine;
  that is exactly the x86_64 `elixos-otp` this repository already builds
  (same version, same configure options), so `ERL_TOP` plus that install on
  `PATH` is the bootstrap.
* **`erl_xcomp_*` answers for configure's runtime probes.** These are the
  values a musl aarch64 Linux has: `erl_xcomp_bigendian=no`,
  `erl_xcomp_linux_clock_gettime_correction=yes`, `erl_xcomp_linux_nptl=yes`,
  `erl_xcomp_linux_usable_sigaltstack=yes`,
  `erl_xcomp_linux_usable_pthread_thread_num=yes`,
  `erl_xcomp_stack_overflow=no`, plus `erl_xcomp_sysroot`/`erl_xcomp_isysroot`
  pointing at the sysroot. `./otp_build configure --host=aarch64-linux-musl
  --build=x86_64-linux-musl …` with the same `--enable-dynamic-ssl-lib
  --with-ssl --without-{javac,wx,odbc,observer,debugger,et,megaco}` as the
  native recipe.
* **What to watch.** The JIT's configure test runs a program, so
  `erl_xcomp_disable_jit` (and/or an explicit `--enable-jit`) has to be set
  deliberately rather than inferred; `STRIP` must be a multi-target strip
  (`llvm-strip`), not the host's; and the two post-install fixes from the
  native recipe (erl as a symlink to erlexec, headers at
  `erts-<vsn>/include`) apply unchanged.

The structure is the same as the kernel's (a native build tool package whose
artifact the aarch64 package installs), but unlike the kernel this one cannot
skip melange's target environment for its *Erlang* half, so the recipe has to
run the bootstrap `erl` from the native OTP install - which is why the plan
above names every input rather than pointing at a flag.

### Where the OTP cross attempt stopped

Two attempts, both run as a standalone `--arch x86_64` melange build (the
shape `kernel-cross.yaml` uses), got the sysroot and the compiler search paths
right and reached `erts/configure`:

* **Alpine signs each architecture's index with its own key.** The guest's
  `alpine-keys` package carries only the x86_64 key, so `apk fetch --arch
  aarch64` answers `UNTRUSTED signature` for the target indexes. The aarch64
  key is `alpine-devel@lists.alpinelinux.org-616ae350.rsa.pub`, published at
  `https://alpinelinux.org/keys/`; installing it in `/etc/apk/keys/` makes the
  fetch verify normally - no `--allow-untrusted` is needed or wanted.
* **The guest has no `/etc/apk/repositories`.** Melange hands repositories to
  apk itself, so a pipeline that fetches extra packages must name them:
  `apk fetch --arch aarch64 -X $repo/main -X $repo/community -o <dir> <pkgs>`,
  and `<dir>` must already exist (`Bad file descriptor` otherwise).
* **Zig's driver does not search a sysroot on its own.** Pass
  `-isystem $sysroot/usr/include -L$sysroot/usr/lib -L$sysroot/lib` alongside
  `--sysroot`; without them `configure` cannot find the target's libraries even
  though the sysroot has them.
* **The next wall is the curses probe**: `checking for tgetent in -lncurses...
  no` and then `configure: error: No curses library functions found`, on a
  sysroot that carries both `ncurses-dev`'s `.so` symlinks and `ncurses-libs`.
  The failing link has to be reproduced with the pinned Zig SDK in hand (a
  probe environment that installs Zig from the shared cache) to see the
  linker's own error - `zig cc` isn't in a minimal environment, and the probe
  that would have shown it had no Zig to run.

Nothing after the curses probe is tested, and the recipe was not kept: an unrun
recipe is scaffolding, not progress. The plan above plus these three findings
are what the next attempt needs.

### The compiler question for OTP: Zig cannot do this one

Two more probes settled the toolchain, and they are the most useful result of
the whole exercise:

* **Zig's driver refuses to link a *dynamic* target library it did not build.**
  With the sysroot's `ncurses-dev`/`ncurses-libs` in place and `-L` pointing at
  them, `zig cc --target=aarch64-linux-musl` answers
  `unable to find dynamic system library "ncurses" using strategy paths_first.
  searched paths: none`. That is by design: Zig links what it ships (its musl,
  its compiler-rt) and treats everything else as static. It is the right
  compiler for our self-contained targets - the shim, `postgres-init`, the
  kernel's `cc` bridge - and the wrong one for ERTS, which links the target's
  `libncurses` and `libssl`.
* **clang + lld + a sysroot is the right shape, and needs the target's GCC
  runtime objects**: `clang --target=aarch64-linux-musl --sysroot=… -fuse-ld=lld`
  fails on `crtbeginS.o`/`crtendS.o` and `-lgcc`, and fetching the target's
  `gcc`/`libgcc`/`libstdc++` into the sysroot did not put `crtbeginS.o` where
  either `-B` or `--gcc-toolchain` expects it (Alpine's aarch64 `gcc` package
  does not ship those objects in `/usr/lib` nor in
  `/usr/lib/gcc/<triple>/<version>/`). That is the next thing to establish -
  where a musl aarch64 sysroot's crt objects come from - and it is a
  prerequisite for everything after it (the `erl_xcomp_*` configure run, the
  arm64 JIT, the Erlang build against the bootstrap ERTS).

Both probes ran in seconds, so the next attempt can iterate quickly; what it
needs is a decision on the sysroot's provenance (the target's package set plus
its GCC runtime, or a purpose-built cross toolchain), not more patience with
one-off flags.

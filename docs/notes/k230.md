# LilyGO T-Display K230

The M30 bring-up gate's output (docs/ROADMAP.md, M28–M33). Surveyed
2026-10-23 from LilyGO's V1.0 schematic, the board's shipped U-Boot device
tree and configs, Canaan's SDKs and documentation, and the mainline Linux,
U-Boot and OpenSBI trees. Facts that only the board can confirm are listed
under [Open on the board](#open-on-the-board); the human-run checklists close
them.

## Boot

### Big core alone

Yes, by construction, with no kernel change. The big core reads `mhartid` 0
(mainline commit `980512a5`: "although docs from Canaan said 1.6GHz Core with
Vector is CPU1, the CSR.MHARTID of this core is 0"), and both cores appear to
be separate single-hart systems with their own PLIC/CLINT view [S6, S3]. So:

- Our device tree describes exactly one CPU, `cpu@0` with `reg = <0>`: the
  big core. A `cpu@1`/`reg = <1>` node would hit
  `BUG_ON(!found_boot_cpu)` (`arch/riscv/kernel/smpboot.c:153`) because SBI
  hands Linux hart 0. The little core is not described at all.
- With one hart, Linux never calls SBI HSM; `CONFIG_SMP=y` is harmless.
- The little core's memory is a `reserved-memory` `no-map` region, 16 MiB at
  `0x07000000`: clear of every address the U-Boot environment loads into, and
  `no-map` because the cores have separate L2 caches with no known coherence.
- Canaan's `k230_linux_sdk` already runs U-Boot, OpenSBI and Linux on the big
  core (`CONFIG_LINUX_RUN_CORE_ID=1`): the SPL on the little core trains DDR,
  releases the big core into U-Boot and parks itself in `wfi` [S3
  `k230_img.c` 259-287].
- The device tree is `boards/t-display-k230/` (ADR-101): mainline v7.3's
  `k230.dtsi` (GPL-2.0 OR MIT) plus the SDIO1 and USB PHY nodes mainline has
  not merged, written to the 7.2.9 bindings, compiled against 7.2.9's
  `dt-bindings` headers.

### C908 kernel config

The C908 uses standard **Svpbmt**, not T-Head's MAE page attributes. The
kernel's T-Head errata (MAE, CMO, PMU) only match `marchid == 0`
(`arch/riscv/errata/thead/errata.c:26-44`), and a core with ratified RVV 1.0
reports a non-zero marchid (`arch/riscv/kernel/cpufeature.c:892-901`). The
little-core hello image prints `marchid` on the board to confirm it.

The firmware must clear MXSTATUS.MAEE (bit 21) before entering S-mode, or the
kernel's PTEs mean "non-cacheable" and it does not boot (commit `980512a5`).
Canaan's U-Boot sets it (`mxstatus = 0x638000`); Canaan's OpenSBI 1.4
overlay clears it for `canaan,kendryte-k230`; mainline OpenSBI (generic
platform, which matches the K230 since v1.5) does not. Hence ADR-102.

Our riscv64 kernel already has every ISA option the core needs: Svpbmt, V,
Zicbom/Zicboz/Zicbop, Zba/Zbb/Zbc. They come from the riscv defconfig, so
`kernel/config.riscv64` now names them for the config guard, together with the
two K230 drivers that have no default: `COMMON_CLK_K230` (without it UART0 has
no clock and the console never appears) and `PINCTRL_K230`.

### Little-core release

The BootROM starts the little core. On SD it loads a "K230"-headed SPL from
1 MiB (copy at 1.5 MiB) into SRAM at `0x80300000` [S4 `firmware_gen.py`,
genimage configs]. The SPL releases the big core into U-Boot.

Canaan's Linux-SDK U-Boot has `boot_baremetal 0 <addr> <size>` [S3
`arch/riscv/cpu/k230/cpu.c` 140-182]. It flushes the image from the big
core's cache, writes the little core's reset vector (`0x91102100`) and pulses
its reset (`0x91101004`: `0x10001000`, `0x10001`, `0x10000`). Mainline
`reset-k230.c` describes the same register as `RST_CPU0`. The SDK's own K230D
configurations already run NuttX on the little core this way before booting
Linux (`bootcmd=run bnuttx; run blinux`).

Ours is `bootcmd=run bcoproc; run belixos`
(`boards/t-display-k230/uboot-env.txt`). It loads `/coproc.bin` from the boot
partition to `0x7000000`, releases the little core into it, then boots Linux.
Reloading the little core later, from Linux, is M32's decision (no mainline
remoteproc; the reset line and reset vector are reachable).

### Memory map

| Range | Size | Use | Linux sees it as |
|-------|------|-----|------------------|
| `0x00000000` | 2 MiB | OpenSBI (`fw_jump`) | reserved by OpenSBI |
| `0x00200000` | ~25 MiB | kernel `Image` | its own |
| `0x07000000` | 16 MiB | the little core: image, heap, stacks | `no-map`, invisible |
| `0x08000000` | 132 KiB | inter-core ring (PROTOCOL §11, capacity 64 KiB per direction) | `no-map`; `/dev/uioN` named `coproc-ring` |
| `0x08100000` | 1.5 MiB | deck framebuffer (PROTOCOL §12) | `no-map`; `/dev/uioN` named `deck-fb` |
| `0x0a100000` | ~90 MiB | initramfs, as loaded by U-Boot | freed after unpacking |

The UIO devices come from `generic-uio` nodes in our device tree
(`uio_pdrv_genirq.of_id=generic-uio` on the command line,
`CONFIG_UIO_PDRV_GENIRQ`); UIO maps physical memory uncached, which the
non-coherent cores need.

### Boot firmware

Mainline U-Boot (`board/canaan/k230_canmv`, since v2025.04) has no SPL, no
DDR training, no MMC and no way to start the little core; its own
documentation relies on the vendor SPL [S7]. ADR-102 therefore pins Canaan's
Linux-SDK U-Boot 2022.10 overlay and OpenSBI 1.4 overlay, built from source
on the build host with Alpine's bare-metal `riscv-none-elf` GCC. It also
wraps the SPL in the plaintext K230 header (`firmware_gen.py -n`'s format;
the AES/SM2 modes use demo keys).

SD layout (LilyGO's, from [S5]):

| Offset | Content |
|--------|---------|
| 1 MiB, 1.5 MiB | SPL (K230 header), two copies |
| `0x1e0000` | U-Boot environment |
| 2 MiB | U-Boot (K230 header + gzip uImage) |
| 30 MiB | p1, ext4 `boot`: `fw_jump.uImage`, `Image`, `t-display-k230.dtb`, `initramfs.cpio.gz`, `coproc.bin` |
| after p1 | p2, ext4 `ELIXOS`: the data disk (`/priv`) |

## Blockers

None. Mainline 7.2.9 can boot the big core alone with our device tree and
Canaan's firmware; the gaps (display, Wi-Fi, PMU, mailbox) are subsystems
that move to the coprocessor or wait, not boot blockers.

## Open on the board

Each is checked by the M30 checklist or noted for the milestone that needs
it:

1. The hello image's `mhartid` (expected 0 on both cores) and `marchid`
   (expected non-zero) on the little core; the kernel log's `riscv,isa` and
   whether Linux boots at all decide the MAEE question.
2. That the TF slot is `mmc 1` in Canaan's U-Boot and SDIO1 in Linux with our
   SDHCI node (the data partition mounts with `elixos.data=/dev/mmcblk0p2`).
3. Which UART the little core should own long-term (UART3 on CH342K
   channel 1 is the proposal, ADR-104), and whether Linux's
   `clk_disable_unused` gates its clock (only the little core's own clocks are
   `CLK_IS_CRITICAL`).
4. The MMC0 pad voltage for the Wi-Fi SDIO (1.8 V bank, 3.3 V pull-ups).
5. The SPI controller and mux function for the LoRa pins (M32/M33).
6. Soft power-off through the K230 PMU (M33).
7. Firmware (ADR-102), all visible on the first boot's console: the BootROM
   accepts our header (and falls back to the 1.5 MiB copy if not); DDR trains
   at LPDDR4-2667; U-Boot probes the size by aliasing (LSDK
   `arch/riscv/cpu/k230/dram.c` `detect_ddr_size`) and its `ft_board_setup`
   writes that size into our device tree's `/memory` at `bootm`, so the
   kernel log's memory line shows what U-Boot found (expected 1 GiB; the
   reserved region is unaffected); the SPL's software inflate of U-Boot
   works; OpenSBI's banner shows the generic platform with the T-Head
   override; `boot_baremetal 0` restarts the little core from the SPL's park
   loop. LilyGO's U-Boot looks for a boot logo on p1 and skips it when absent.

## Deck profile

ADR-111. 1 GiB of RAM, minus 16 MiB for the little core and OpenSBI's
2 MiB, leaves Linux about 1006 MiB. The deck image is the riscv64 image plus
the board files, with the heavy services off by default: PostgreSQL starts on
first use instead of at boot, Oban follows it, and the Oh-My-Jido coding
runtime does not start at boot. The browser is already absent on riscv64
(ADR-097); the Emerge renderer is present. `make deck-image` builds it in M33.

Baseline, measured with the M30 riscv64 image on QEMU virt with 1 GiB (the
M28 smoke test, 2026-10-23): `MemTotal` 988388 kB, `MemAvailable` 554468 kB
at `iex(1)>` with every service started. The root filesystem is the unpacked
initramfs, held in RAM; the board budget is measured again in M33.

## Bring-up images

`make k230-bringup` builds `build/k230/elixos-k230-bringup.img`: the firmware
(ADR-102), the riscv64 `Image` and `initramfs.cpio.gz`, our DTB, the hello
image as `coproc.bin`, and an empty data partition. The kernel command line
is `console=ttyS0,115200 earlycon panic=-1 elixos.live=1`: step 1 needs no SD
driver once U-Boot has loaded the files.

## Hardware checklists

Human-run; images and scripts are prepared before each step.

### M30: bring-up gate

Setup: write the image with
`dd if=build/k230/elixos-k230-bringup.img of=/dev/<card> bs=4M conv=fsync`,
insert it, connect USB-C **J2** to the host (power plus the CH342K), open the
first of its two serial ports at 115200 8N1 (for example
`picocom -b 115200 /dev/ttyACM0`), and hold SW2 for 3 s if the board does not
power on by itself.

- [ ] Our image boots on the big core to the shim's banner and `iex(1)>` on the
  serial console. Expected: U-Boot's banner, OpenSBI's banner, the kernel log
  with one CPU, then the shim's lines (docs/PROTOCOL.md §6) and `iex(1)>`.
- [ ] The little core runs a trivial image we loaded. Expected, between
  U-Boot's `boot_baremetal` and OpenSBI's banner:
  `elixos coproc: hello from the little core mhartid=0x... marchid=0x...`.
  Record both values here.
- Optional, for M31: at the prompt, `File.ls!("/dev")` lists `mmcblk0p1` and
  `mmcblk0p2`. Record the kernel log's `mmc` lines if not.

### M31: inter-core link

- [ ] Ping across the link.
- [ ] Distribution comes up over it.
- [ ] Latency and throughput recorded.

### M32: AtomVM on the little core

- [ ] The little core boots AtomVM.
- [ ] It joins Elixos.
- [ ] It survives a BEAM crash on the big core.

### M33: the deck

- [ ] Boots to IEx on the AMOLED.
- [ ] Touch and the on-screen keyboard work.
- [ ] `Node.list()` shows the coprocessor.
- [ ] A LoRa message arrives as a message.
- [ ] Killing the BEAM keeps the panel alive and the session comes back.
- [ ] Save, reboot, still there.
- [ ] Poweroff powers off.

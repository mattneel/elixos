# melange and apko on this machine

What M16 (the Alpine image build, ADR-041) cost to learn. The build tools
themselves are pinned in `scripts/install-build-tools.sh` (melange v0.62.0,
apko v1.4.10, both by sha256).

## melange

- Building the kernel's `tools/` (objtool) needs a system `asm/types.h`: on
  Alpine that is the `linux-headers` package, on glibc distros it is there
  already (linux-libc-dev). Without it objtool fails with "asm/types.h: No such
  file or directory".
- The x86_64 kernel build also needs `gawk`. BusyBox awk rejects the literal
  `{` in mainline `scripts/orc_hash.sh`; its pipeline can still exit zero and
  emit the hash of empty input. Adding `gawk` to the melange build environment
  fixes the ORC metadata without patching Linux. A fresh packaged build must
  have no `awk: bad regex` warning as well as passing the config guard.
- `--source-dir` does **not** bind your tree read-only: melange *copies* it
  into its workspace, which it then binds at `/home/build`. Pointing it at the
  repo root once copied 55G (the kernel tree, `os/_build`, `os/tmp`). Stage a
  small directory instead - only what the package's pipeline reads. Dotfiles
  (`.zig-version`, `.tool-versions`) must be named explicitly when staging;
  the package pipelines read them for their version assertions.
- The copy is writable, so a pipeline can build in place (`cd /home/build`);
  no copying into `/tmp` is needed.
- `melange keygen` writes `melange.rsa`/`melange.rsa.pub`. The private key is
  the dev signing key: `build/` is gitignored, so it stays out of git.
- `--out-dir` becomes an APK repository (an `APKINDEX` is generated by
  default); apko consumes it with `-r`/`--repository-append` and the public key
  with `-k`/`--keyring-append`.
- aarch64 packages on an x86_64 host run under binfmt emulation
  (`qemu-aarch64` registered, docker for the `docker` runner if wanted). This
  machine has both; `scripts/check-tools.sh` reports them.
- The first aarch64 image build on this x86_64 WSL host took 5,143 seconds;
  the next `make image` assembled both architectures from cached APKs in
  51 seconds. Kernel-fragment preflight is cheap; emulated kernel and OTP
  compilation is not. Delete only the APK whose sources changed to rebuild
  it, or use `FORCE=1` when every package really needs rebuilding.
- A cold on-box C toolchain smoke in a 1 GiB aarch64 TCG guest took 480
  seconds: the pinned Zig ran, the `cc` bridge built a static musl binary,
  that binary exited 23, and the VM cwd stayed `/`. Keep this separate from
  the boot/save/restore smoke, which does not run the native C compiler.
- The build environment needs its own packages (busybox, curl, tar, xz for the
  shim); the repositories in the YAML are the same pinned Alpine release apko
  uses.
- A melange APK is a plain tar stream as far as `tar` is concerned: `tar -xzf
  pkg.apk` works, without apk-tools on the host (`apk` itself is not installed
  here). The checksum xattr is just a warning (`--warning=no-unknown-keyword`),
  and naming the directories wanted (`tar -xzf pkg.apk -C dir toolchain`) skips
  the `.PKGINFO`, signature and SBOM metadata.
- Kernel fragments are named after melange's `build.arch` values - `x86_64`
  and `aarch64` - because the kernel package reads
  `kernel/config.${{build.arch}}`. An `arm64` file builds nothing and fails
  with "The merge file .../config.aarch64 does not exist".
- The common kernel fragment must stay arch-neutral: `CONFIG_I6300ESB_WDT` and
  `CONFIG_SERIAL_8250*` are x86 symbols, and the per-architecture guard fails
  the arm64 build on them (that is the guard doing its job).
- Kernel fragments can be pre-flighted on the host in seconds - `make
  ARCH=arm64 defconfig`, `merge_config.sh`, `make olddefconfig`, then
  `scripts/check-kernel-config.sh` - before paying for an emulated build.
  `unset LLVM` first: this machine's environment exports `LLVM`, and kbuild
  refuses ("Invalid value for LLVM").

## apko

- `apko lock <config>` exists but is hidden from `apko --help`. The lockfile
  is bound to the config's **checksum**: change the config and every build
  fails with "checksum ... does not match ... (maybe regenerate the lock
  file)". So locks are per package set and per architecture, and a config
  change means `apko lock` again.
- `apko build` emits an OCI-shaped tar (a `*.tar.gz` layer, `manifest.json`,
  `index.json`), takes `--lockfile`, `--build-date` (reproducibility),
  `--sbom-path` (SPDX, one entry per package with its version) and
  `--cache-dir` (our local mirror).
- `apko build-minirootfs` has **no** `--lockfile` and takes `--build-arch`
  instead of `--arch`; use `apko build` and take the layer.
- Keys can be committed: the config's keyring may name a repo-local path
  (`apko/keys/...`), and the lockfile embeds the key material too.
- The layer's device nodes cannot be extracted without root. They do not need
  to be: the tar carries major/minor, and `gen_init_cpio` can declare them.

## Packing the initramfs

- `paths` is a top-level key in apko's config, **not** under `contents`; it is
  how a directory that no package ships exists at all. A missing `/priv` sent
  the first apko boot straight to rescue (`Elixos.info` said `mode: :rescue`):
  the shim cannot mount the persistent disk onto a path that is not there.
- Do not mix pipelines inside one root filesystem. Overlaying the old
  hand-built `/lib/ld-musl-x86_64.so.1` on Alpine's makes BusyBox segfault
  (exit 139) while the old factory still runs. During the transition, keep
  Alpine's loader and let the old ERTS use it.
- `gen_init_cpio` list syntax, per entry kind:
  - `dir <name> <mode> <uid> <gid>`
  - `file <name> <location> <mode> <uid> <gid>` - location before the mode,
    unlike the others (getting this wrong is "Unrecognized file format")
  - `slink <name> <target> <mode> <uid> <gid>`
  - `nod <name> <mode> <uid> <gid> <c|b> <major> <minor>`
- `-t 0` stamps every entry at the epoch; `gzip -9n` (no name, no timestamp)
  makes the archive reproducible.
- `scripts/mkinitramfs.sh` reads the layer tar with python3 and emits that
  list: ownership, modes and device nodes come from the tar, so nothing in the
  packing path needs root.

## The factory release and OTP

- `mix release` with `include_erts: false` takes the ERTS *and the OTP
  applications* from the system: the release carries only this project and its
  Hex dependencies. Elixos installs OTP as its own package (`elixos-otp`) and
  the release points at it - `/factory/erts` and `/factory/erts-<vsn>` as
  symlinks to the install, plus a symlink for every app in the OTP install's
  `lib/` that the release does not carry itself. Without those links the BEAM
  starts and dies before the prompt (it writes a crash dump under
  `/priv/crash/`), because the boot script's `$ROOT/lib` is the release's.
- The same package makes `erl` a symlink to `erlexec` inside the installed
  ERTS and copies the headers to `erts-<vsn>/include`, which is where
  `:code.root_dir()` sends a NIF build.

## Test hygiene

- The QEMU harness reads prompts off the console, and `QEMU.iex/3`'s contract
  is a console sitting at a prompt the harness has already consumed. A test
  that types several expressions must thread the VM between the calls: M14's
  two-repo test used a `for` comprehension, dropped each iteration's VM, and
  typed into a console two prompts ahead of what the harness believed - the
  harness then matched the prompt still on screen and returned the echoed
  input alone, about one run in three. It looked like a harness timing bug for
  a while; ADR-042 records the rule. `iex/3` also anchors on the echo of the
  line it sent (whitespace flexible; a five-second window, because a
  multi-line expression's redraws can split the echo) and compares each
  matched prompt by its own number. Keep expressions short anyway.
- A killed QEMU run leaves its `@moduletag :tmp_dir` behind, and each holds a
  copy of the disk image: `os/tmp` reached 19G once. When the disk looks
  wrong, `rm -rf os/tmp/*` is safe - the tests recreate it.
- A daemon returned by `:ssh.daemon/2` is already a child of OTP's
  `:sshd_sup`. Returning that PID as an Elixos supervisor child does not
  reparent it: Elixos's shutdown signal is not from its parent, so Elixos
  waits five seconds and force-kills it. The aarch64 demo exposed the
  resulting `{:sshd, :acceptor_sup}` crash report. `Elixos.SSH` now owns a
  small GenServer that traps exits, monitors the daemon and calls
  `:ssh.stop_daemon/1` on termination. The regression checks normal daemon
  exit, EOF on an open connection and refusal of new connections.
